# Deploy StudyAI as a controlled private beta on Render

This guide is for the first real-user beta, not a broad public launch.

## Why this configuration

StudyAI currently uses SQLite for accounts, synced state, question reports, and client-error records.
Render's normal service filesystem is ephemeral, so the SQLite database must be placed on a persistent
disk for any beta where user data matters.

The supplied `render-private-beta.yaml` therefore uses:

- Python web service
- Singapore region
- one service instance
- one Gunicorn worker with four threads
- `/api/health` health checks
- SQLite at `/var/data/studyai.db`
- a persistent disk mounted at `/var/data`
- HTTPS secure cookies
- trusted proxy handling
- an invite-only registration code
- finite Personal AI daily limits

**Important:** Render persistent disks require a paid web service. Do not create the Blueprint until
you have reviewed the cost shown by Render.

## Before creating the service

1. Make sure GitHub Actions is green on `main`.
2. Create a strong private-beta invite code (do not commit it).
3. Decide whether Personal AI will be enabled. If yes, have the Gemini API key ready.
4. Keep social OAuth disabled initially unless its final HTTPS callbacks are configured.

## Create the Render Blueprint

Render Blueprints use `render.yaml` by default, but you can choose a different Blueprint file.
Point the Blueprint at:

`render-private-beta.yaml`

Review every resource before confirming creation.

The Blueprint will prompt for:
- `BETA_ACCESS_CODE`
- `GEMINI_API_KEY`

`SECRET_KEY` is generated by Render.

## Verify environment before launch

In a production-like shell with the same environment variables, run:

```bash
python production_preflight.py
```

The checker does not print secret values.

## First deployment smoke test

After Render reports the deployment healthy:

1. Open `/api/health` and confirm `database: ready`.
2. Open the site in an incognito/private window.
3. Verify account creation rejects an incorrect beta code.
4. Create one disposable beta account with the correct code.
5. Complete onboarding.
6. Start a guided Today session.
7. Answer practice and confirm evidence/mastery updates.
8. Refresh and sign out/in to confirm persistence.
9. Run a SAT Math mock and open the College Board Desmos calculator.
10. Send a test question report.
11. Test Personal AI only with non-sensitive sample notes.
12. Download the disposable account's data.
13. Delete the disposable account and verify it can no longer sign in.

## Invite the first testers

Start with roughly 5–10 students. Give each tester:
- the beta URL
- the private beta access code
- a short request to use the site naturally and report confusion

Do not give a long tutorial first. The onboarding and Today page need to stand on their own.

## What to measure

StudyAI records privacy-light beta signals in normal account state:
- distinct active days
- first recorded practice
- guided sessions started
- guided sessions completed
- last active time

It does not need a student's school name, phone number, address, precise location, or date of birth.

## Before a broader public launch

Do not scale the SQLite/disk setup horizontally. First add:
- PostgreSQL
- email verification
- password-reset email delivery
- persistent/distributed rate limiting
- final production OAuth configuration
- operational monitoring and backup procedures

Then remove or rotate the private-beta invite gate when open registration is actually intended.
