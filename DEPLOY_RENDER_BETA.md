# Deploy StudyAI as a controlled private beta on Render + Neon

This guide is for the first real-user beta, not a broad public launch.

## Architecture

StudyAI now supports two database backends:

- local development can continue using SQLite at `studyai.db`;
- hosted beta/production should use PostgreSQL through `DATABASE_URL`.

For the hosted beta, use Neon PostgreSQL. The Render service no longer needs a persistent disk.

The supplied `render-private-beta.yaml` uses:

- Python web service
- Singapore region
- one service instance
- one Gunicorn worker with four threads
- `/api/health` health checks
- PostgreSQL through the secret `DATABASE_URL`
- HTTPS secure cookies
- trusted proxy handling
- an invite-only registration code
- finite Personal AI daily limits

Keep one app instance during the first beta because StudyAI's rate limiter is still process-local. PostgreSQL itself is no longer the scaling restriction.

## 1. Create the Neon database

Create a Neon PostgreSQL project and choose a region close to the Render service, preferably Singapore when available.

From Neon Connection Details, copy the pooled PostgreSQL connection string. Neon pooled connection strings use the `-pooler` hostname and are appropriate for the hosted web app.

The connection string is a secret. Never commit it to GitHub, paste it into source code, or put it in browser JavaScript.

Store it as:

```env
DATABASE_URL=postgresql://...
```

The Neon connection should use TLS.

## 2. Migrate existing SQLite data

Before the first hosted launch, keep a backup copy of `studyai.db`.

Install current requirements:

```bash
python -m pip install -r requirements.txt
```

Set `DATABASE_URL` in your local `.env` or shell, then run:

```bash
python migrate_sqlite_to_postgres.py --source studyai.db
```

The migration tool:

- refuses to write into a non-empty PostgreSQL database;
- preserves existing account IDs and foreign-key relationships;
- copies accounts, OAuth identities, synced state, question reports, and client diagnostics;
- resets PostgreSQL identity sequences;
- verifies source/target row counts;
- never prints the database connection string.

After migration, verify again without writing:

```bash
python migrate_sqlite_to_postgres.py --source studyai.db --verify-only
```

Keep the SQLite file as a temporary offline backup until the Neon-backed version has been tested successfully.

## 3. Before creating the Render service

1. Make sure GitHub Actions is green on `main`.
2. Create a strong private-beta invite code.
3. Have the Neon pooled `DATABASE_URL` ready.
4. Decide whether Personal AI will be enabled. If yes, have the Gemini API key ready.
5. Keep social OAuth disabled initially unless final HTTPS callbacks are configured.

## 4. Create the Render Blueprint

Point Render at:

`render-private-beta.yaml`

The Blueprint will prompt for:

- `DATABASE_URL`
- `BETA_ACCESS_CODE`
- `GEMINI_API_KEY`

`SECRET_KEY` is generated by Render.

No persistent disk is required for the database because account data lives in Neon PostgreSQL.

## 5. Verify environment before launch

Run:

```bash
python production_preflight.py
```

The checker verifies that PostgreSQL is configured and never prints secret values.

## 6. First deployment smoke test

After Render reports the deployment healthy:

1. Open `/api/health` and confirm `database: ready` and `backend: postgresql`.
2. Open the site in an incognito/private window.
3. Verify account creation rejects an incorrect beta code.
4. Create one disposable beta account with the correct code.
5. Complete onboarding.
6. Start a guided Today session.
7. Answer practice and confirm evidence/mastery updates.
8. Refresh and sign out/in to confirm PostgreSQL persistence.
9. Run a SAT Math mock and open the College Board Desmos calculator.
10. Send a test question report.
11. Test Personal AI only with non-sensitive sample notes.
12. Download the disposable account's data.
13. Delete the disposable account and verify it can no longer sign in.

## 7. Invite the first testers

Start with roughly 5 to 10 students. Give each tester:

- the beta URL;
- the private beta access code;
- a short request to use StudyAI naturally and report confusion.

Do not give a long tutorial first. The onboarding and Today page need to stand on their own.

## 8. Before broader scaling

PostgreSQL removes the SQLite single-file limitation, but StudyAI still needs these before a broader public launch:

- email verification;
- password-reset email delivery;
- persistent/distributed rate limiting before multiple app instances;
- final production OAuth configuration;
- operational monitoring and database backup procedures.

When those are ready, Render can use more workers/instances without relying on a single SQLite writer.
